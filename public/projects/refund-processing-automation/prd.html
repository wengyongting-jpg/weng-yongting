Refund Processing Automation

Author: Yongting Weng (Workflow designer)  ·  Status: Design & demo  ·  Version 1.0

01 · PROBLEM

Manual handling is slow; full automation is unsafe

  • Receipt information is stored in documents, not structured data — every case requires manual extraction.
  • Manual extraction is repetitive and inconsistent across operators.
  • Some cases should not be auto-processed — rule violations or low confidence demand human judgement.
  • Full automation removes human judgement where it is genuinely needed.

02 · DESIGN DECISION — CONFIDENCE THRESHOLD ROUTING

DECISION 01

Full automation vs. confidence-based routing?

Compared: A · End-to-end automation for all valid receipts. B · Confidence scoring with a human-review boundary.

Chosen: B — a confidence threshold is the only defensible boundary between automation and risk.

Evidence: Receipt quality varies wildly (scan quality, handwriting, partial data). A universal auto-pass rule will fail on edge cases.

Validate via: Run the confidence model on a labelled test set and set the threshold at the point where precision meets the business SLA.

04 · STRUCTURED DATA MODEL

The extraction layer returns these six fields:

  • Receipt ID
  • Merchant
  • Date
  • Total Amount
  • Refund Reason
  • Confidence Score

05 · SUCCESS CRITERIA & VALIDATION

North Star: proportion of cases handled end-to-end without human touch (measured against total volume).

Safety metric: zero auto-processed cases that fail rule validation.

Current status: workflow design and demo. Production metrics (accuracy, processing time, auto-rate) are not claimed because the design has not been deployed.

06 · ITERATION PLAN

  • Now — run the confidence model on a labelled test set to set and justify the threshold.
  • Next — pilot the workflow on 200 real refund cases, measuring auto-rate, error rate, and operator override rate.
  • Later — tune the extraction model by feeding operator corrections back as training data.
